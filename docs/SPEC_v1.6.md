## 1. 会话改名、回退后照样认人

**问题（真实发生）**：Claude 信箱按会话标题认人。T0 把会话改名为「‼️POSTOFFICE」后，钩子日志连续记“未登记会话”，信进不来，直到人工重登记。钩子 payload 里的 CLI `session_id` 也不稳定：同一个桌面会话因回退先后换了 3 个 CLI id。

**稳定身份（已实测，2026-10-05 修订）**：Claude 桌面 App 启动会话进程时设置环境变量，钩子子进程会继承（已在 manager 正在运行的钩子进程环境里核实）：
- `CLAUDE_CODE_HOST_SESSION_ID=local_<X>`：桌面会话 id，回退、改名都不变；fork 得到新 id。
- `CLAUDE_CODE_ENTRYPOINT=claude-desktop`：区分桌面版与命令行版。
**首选这两个环境变量**，不需要解析日志。仅当 `ENTRYPOINT=claude-desktop` 但 `HOST_SESSION_ID` 缺失时，才用 `~/Library/Logs/Claude/main*.log` 中 `Mapping internal session local_<X> to CLI session <Y>` 按**本次 payload 的 CLI session_id 精确**反查（多文件时按行内时间戳取最新，不按文件名猜；路径可用 `POSTOFFICE_CLAUDE_MAINLOG` 覆盖）。不在 transcript 全文里找旧 id。命令行版（ENTRYPOINT 不是 claude-desktop）用 payload 的 CLI `session_id` 作为身份。

**匹配规则（按顺序，互斥）**：
1. 解析到身份 X，且恰有一个信箱 `claude_session == X` → 就是它（标题不同也认；把 `claude_title` 更新为当前标题并记日志）。若有多个信箱绑定同一 X → 不认任何一个，诊断通知人一次。
2. 解析到身份 X，没有信箱绑定 X，且当前标题**恰好匹配一个未绑定**的信箱 → 自动绑定 X 并记日志。
3. 解析到身份 X，标题匹配的信箱已绑定**别的**身份 → 不认（同名不接管），立即通知人一次（同一对 身份/信箱只通知一次）。
4. 身份解析不到：标题匹配**未绑定**信箱 → 按标题认（兼容旧登记）；标题匹配**已绑定**信箱 → 不认，诊断通知人一次（不静默认领）。
5. 其他（未登记的普通会话）→ 静默退出，不通知。
- 任何解析异常都走上面的降级分支，钩子不得报错退出。
- routes 中 Claude 信箱字段 `claude_session`（manager、art_d 已有，沿用）；`postoffice add <信箱> --claude "<标题>" [--claude-session <id>]`；`doctor` 显示绑定状态。

## 2. 只为真正耽误事的信提醒人

**问题（真实发生）**：“提醒后 30 分钟未处理”4 次全是仅告知的政策广播/广播汇总；02:22 一封旧积压信在信箱上线后 6 秒就被报“20 分钟未送达”，1 秒后实际已唤醒（按信件创建时间计时导致误报）。

**行为**：
- 30 分钟未处理提醒（check_consumed）只对**需要处理**的信生效。分类优先级（从上到下，先命中先定）：
  1. 回执通知（有 `回执：` 头）、广播汇总 → 不需处理；
  2. `需要：` 的值（先去掉重复的“需要：”前缀）**恰好等于**标准词：`回复` / `审核` → 需要处理；`仅告知` → 不需处理；
  3. 自由文本只含否定类词（仅告知 / 无需 / 不用回 / 默认不答复 / 无需操作）且不含肯定类词 → 不需处理；只含肯定类词（回复 / 审核 / 处理 / 修改 / 决定 / 确认）且不含否定类词 → 需要处理；
  4. 正负混合（如“仅告知，无需回复/确认”）或都不含 → **未知 → 照旧提醒**（不宣称零误报）。
  不按标题或正文猜。`send` 的“需要”参数若已以“需要：”开头，写信时去掉重复前缀。
  分类函数集中一处，文档里写清推荐的标准写法（`需要：回复` / `需要：审核` / `需要：仅告知`）。
- 20 分钟未唤醒 / 未送达计时：起点改为 `max(信件写入时间, 该信箱最近一次转为在线的时间)`，离线时长不计入。`online_since` 存 routes.json，**只在真正 offline→online 时更新**（重复点“在线”不刷新，否则会永远推迟告警）；CLI 与面板都走同一个 `apply_status`。升级时已在线、没有 `online_since` 的信箱：基线取“邮递员首次以新版运行的时间”并写入，避免升级瞬间按旧文件年龄集中误报。
- 广播本身是否需要处理看它自己的 `需要：`，不因是广播一律免提醒。

## 3. 回执合并成一条，排在正式信后面

**问题（真实发生）**：01:44–01:48 给 postoffice_codex 投了 3 份交付 + 3 条回执，触发限流，01:48:37 的“发布完成”正式信晚了约 6 分钟才送达。

**行为（T0 定）**：同一信箱同一次唤醒里，**正式信在前，回执合并成一条放最后**，例如：
```
另有 3 条回执（默认不答复，需要时按 ID 查询）：
- postoffice_lab：<原事由短句>  查询：postoffice receipt <信箱> '<ID>'
- manager：……
- art_d：……
```
- Claude 钩子：本来就把多封新信放在一次唤醒里 —— 改为正式信在前、回执合并块在后。
- OpenCode 插件：有正式信时先投正式信（一次一封，照旧）；没有正式信时，把积压的回执合并成**一条**投出去。回执最多等 10 分钟：超过 10 分钟就随下一次投递一起带上，不能被正式信永远挤掉。
- codex_queue（邮递员）：同上——正式信逐封先排；回执合并成一条 queue 消息。
- 限流按“唤醒次数”算：合并后的一条只算 1 次——三条通道都要改，包括 Claude 钩子现在的 `rate_mark(name, len(files))`。“随正式信一起带上的到期回执”也只算这 1 次。
- 批量记账：批内每个 ID 只在这次投递**整体被接受后**才记已送达；投递失败释放这些 ID 的认领（claims），不误消费；多实例争抢同一批不双投；已投递的 ID 不再进入重试批。
- 10 分钟是“到期后随下一次投递优先带上”，不是在忙碌 / 离线 / 限流时强行唤醒的硬时限；总限流仍然有效。
- 归档仍按单个 ID 调用现有 `archive-receipt`，不扩展多 ID / all（本次不做）。

## 测试（加进 tests/smoke.sh，全在临时目录）
1. 认人：假 main.log 映射 CLI id→local id；信箱绑定该 local id 后，标题改成别的仍被唤醒；`claude_title` 被更新。
2. 回退：同一 local id 换一个新 CLI id，照样认人。
3. 同名不接管：另一个 local id、同标题 → 不认，通知人恰好一次（再触发不重复）。
4. 无 main.log：退回标题匹配，钩子不报错。
5. 首次自动绑定：标题匹配 + 能解析 local id → 写入 `claude_session`。
6. 30 分钟提醒：需要“回复”的信会提醒；“仅告知”、回执通知、广播汇总不提醒；无法识别的会提醒。
7. 20 分钟计时：信写于 1 小时前、信箱刚转在线 → 不立即告警；在线后满时限才告警（用环境变量把时限缩到秒级）。
8. 合并回执（用 01:44 的真实形态复现）：给 codex 假信箱 3 封正式 + 3 条回执 → 正式信先送、3 条回执合并成 1 条消息且含 3 个 ID；不触发限流；每个 ID 账本都记已送达；重跑不重复。
9. 回执不饿死：只有回执时会合并投出；正式信持续时，超过 10 分钟的回执随下一次投递带上（仍只算 1 次唤醒）。
11. 认人负例：多个信箱绑定同一身份 → 不认、通知一次；身份解析不到 + 标题匹配已绑定信箱 → 不认、诊断一次；ENTRYPOINT 非桌面时用 CLI session_id。
12. 分类负例：“仅告知，无需回复/确认” → 未知 → 提醒；“需要：需要：回复” → 回复。
13. online_since：重复设为在线不刷新；升级基线不导致集中误报。
14. 批量失败：模拟投递失败 → 批内 ID 都不记已送达、认领释放；重试不重复已送达的 ID。
10. 原有测试全部继续通过；`/usr/bin/python3 -m py_compile postoffice`；`node --experimental-strip-types --check opencode/postoffice.ts`。
